# Vision evaluation — 2026-08-30

## Outcome

The multimodal path is functional and grounded enough to identify the primary
defect in most fixtures, but it does **not** meet the 8/10 release gate.

| Run | Model | Input detail | Strict passes | Mean latency |
|---|---|---|---:|---:|
| Initial baseline | `gpt-4o-mini` | low | 3/10 | 2.62 s |
| Tuned prompt | `gpt-4o-mini` | high | 5/10 | 3.04 s* |
| Model comparison | `gpt-4o` | high | 6/10 | 1.98 s |

\* The tuned mini run resumed after provider rate limits; one successful case
includes retry delay, so its latency is not a clean performance benchmark.

The strict score requires decisive visible facts to appear verbatim, useful
reproduction steps, concise output, and no configured forbidden claim. Human
hallucination review remains required.

## What improved

- High-detail images and explicit chronological frame labels improved exact
  error/status extraction.
- The tuned prompt produced exact evidence for duplicate payment, stuck loader,
  checkout validation, and upload progress cases.
- `gpt-4o` improved the strict result by one case and completed all ten cases
  without evaluation errors.
- No configured forbidden claim appeared in either completed tuned run.

## Why the gate still fails

1. The report schema requires reproduction steps, but sparse frames do not
   prove the actions between states. Both models sometimes infer button clicks,
   edits, or resolution actions.
2. Models often identify the primary defect while omitting secondary evidence
   required by the strict manifest, such as invoice identifiers or table
   status.
3. Some fixture text is intentionally clipped or low-contrast, limiting exact
   OCR even when the visual defect is correctly recognized.
4. Screen frames and browser/OS metadata do not contain user intent, expected
   behavior, pointer events, or typed-input history.

## Decision

Do not claim that BugSathi automatically reconstructs exact reproduction steps
from video alone. The defensible claim is:

> BugSathi grounds a structured draft report in selected recording frames and
> environment metadata, while preserving uncertainty where the capture does not
> prove the triggering action.

Before calling the feature release-ready, add one of:

- a short user-supplied issue description and expected behavior;
- captured interaction metadata (click target, route, input changes); or
- an explicit `unknowns`/`inferred_steps` field that separates observation from
  inference.

Then rerun the same ten fixtures without weakening expected facts merely to
raise the score.

## Reproduction

```bash
./scripts/capture-vision-fixtures.sh
go test ./scripts/vision-eval
go run ./scripts/vision-eval -env .env \
  -out docs/evaluation/results/YYYY-MM-DD.json
```

The evaluator loads only `AI_*` variables from `.env` and never writes the API
key to results.
